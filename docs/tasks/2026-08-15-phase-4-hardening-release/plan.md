# Phase 4 — Hardening + Release

**Status: PLANNED** — implementation belongs to a separate dev-coordinator
session. See `docs/DEVELOPMENT_PHASES.md` for the phase definition.

## Objective

Ship a production-ready Windows build of the Toolbox. After this phase the
installer produces a working app, the critical processing paths are covered by
tests, and the app degrades gracefully on real-world edge cases.

Concrete outcomes:

- Edge cases handled gracefully (large batches, permission errors,
  missing/moved destinations, corrupt files, zero-byte files, extremely large
  images).
- Rust unit + processor integration coverage for the paths listed in
  `DEVELOPMENT_PHASES.md` (collision resolution, path safety, resize math,
  aspect ratio, logo presets, validation, error mapping, format conversion,
  output dimensions, batch partial failures, Logo Pack contents, no source
  overwrite).
- Frontend interaction-state tests (no test framework exists yet — this phase
  introduces Vitest + React Testing Library).
- Batch concurrency / memory behavior verified and documented.
- Windows NSIS installer via the Tauri bundler, with a real (generated) app
  icon and correct metadata.
- Per-tool preference persistence (last format/quality, Logo Pack asset
  selection) — owner-approved addition beyond the literal phase list.

## Decisions and constraints

1. **Installer = NSIS.** Tauri-bundled NSIS (no WiX/extra tooling). Enable
   `bundle` in `tauri.conf.json` with `targets: ["nsis"]`.
2. **Branding generated by the implementer.** Produce a simple, neutral
   "toolbox/utility" mark consistent with `UI_GUIDELINES.md` (no gradients, no
   bright accents, restrained), regenerate the full icon set via
   `npm run tauri icon <source>`, keep `productName` `"Toolbox"`. Do not change
   the identifier.
3. **Tool-preference persistence is in scope** (owner decision). Persist, via
   the existing single settings service/store: converter last `format` +
   `quality`, compressor `quality`, and Logo Pack selected `assetIds`. **Resize
   is out of scope** (owner asked for format/quality/asset-selection only).
4. **Extremely-large-image guard is added to decode, not inspect.** `inspect`
   is already header-only. `decode` (used by convert/compress/logo-pack) gains
   a pre-decode dimension/pixel check. Introduce named constants
   (`MAX_DIMENSION` 16 384 px/side, `MAX_PIXELS` 64 000 000) and return
   `INVALID_IMAGE` ("Image too large: W × H") when exceeded. Thresholds are a
   judgment call and are centralized constants for easy tuning (see Risks).
   The implementer must verify the exact `image` 0.25 API for reading
   dimensions header-only before full decode (consistent with prior phases'
   crate-API verification discipline).
5. **`run_batch` becomes runtime-agnostic.** Refactor it to take a progress
   callback (`impl Fn(u32, u32, &str) + Sync`) instead of `&tauri::AppHandle`,
   mirroring `logo_pack::generate`. Commands wrap the callback in `app.emit`.
   This makes batch partial-failure and large-batch tests runnable without a
   Tauri app, and matches ARCHITECTURE §35 ("processors testable without
   rendering the UI").
6. **Concurrency stays `min(available_parallelism, 4)`** unless profiling shows
   otherwise; peak memory is bounded by ~4 concurrent full decodes. Document the
   rationale in `batch.rs` and ARCHITECTURE §28. Real-world profiling of a large
   batch is an owner/coordinator activity (see Validation).
7. **Frontend tests use Vitest + React Testing Library + jsdom** — the minimal
   standard addition, justified because Phase 4 explicitly requires frontend
   tests and none exist. Mocks are placed in a `src/test/` helper that fakes the
   `@/services/tauri` adapter, `@/services/settings`, and the
   `@tauri-apps/api/webview`/`@tauri-apps/plugin-*` modules so components render
   outside a Tauri runtime.
8. **Local-first / non-destructive / no network hold.** No new network
   dependencies; paths remain `Path`/`PathBuf`; frontend input stays untrusted at
   the command boundary.
9. **Doc reconciliation is scoped and minimal.** Update ARCHITECTURE.md only for
   durable changes (image-size guard in §17/§28, tool-preference persistence in
   §21, NSIS packaging in §33) and fix the stale 6-phase split in §32 to match
   `DEVELOPMENT_PHASES.md`. `report.md` and the root `CHANGELOG.md` entry remain
   the coordinator's responsibility (per AGENTS.md / sol-planner), not this
   plan's tasks.

## Implementation tasks

Tasks 1–3 (Rust) and 4–5 (frontend) have **non-overlapping writable areas** and
can run concurrently. Task 6 depends on 4 and 5. Task 7 (packaging) runs last,
after 1–6 all pass. Task 8 (docs) runs last.

### Task 1: Rust — decode guard + corrupt/zero-byte coverage

- Goal: Prevent OOM on extremely large PNG/JPEG and prove corrupt/zero-byte
  files degrade to clean errors instead of panicking.
- Relevant files:
  - `src-tauri/src/tools/image/decode.rs`
  - `src-tauri/src/services/inspect.rs`
- Implementation guidance:
  - Add `const MAX_DIMENSION: u32 = 16_384;` and
    `const MAX_PIXELS: u64 = 64_000_000;` in `decode.rs`.
  - In `decode`, read dimensions header-only first (open → `with_guessed_format`
    → dimension read) and reject when either side exceeds `MAX_DIMENSION` or
    `width * height` exceeds `MAX_PIXELS`, returning
    `ProcessingError::invalid_image(format!("Image too large: {w} × {h}"))`,
    before the full decode. Verify the exact 0.25 API for a header-only
    dimension read (the WebP branch already has an implicit guard via
    `output_buffer_size`; keep it).
  - Add a `#[cfg(test)]` module to `decode.rs`: (a) a corrupt `.png` (valid
    extension, garbage bytes) → `decode` returns `Err` (never panics), mapped to
    `UnsupportedFormat`/`DecodeFailed`; (b) a zero-byte file → `Err`, no panic;
    (c) a synthetic over-limit image (construct a `DynamicImage` whose width
    exceeds `MAX_DIMENSION`, save it, then assert `decode` returns
    `InvalidImage`).
  - Add a `#[cfg(test)]` module to `inspect.rs`: zero-byte file and corrupt
    `.png` are flagged `status == "invalid"` with a non-empty `error`; a valid
    PNG returns `status == "ready"` with correct dimensions.
- Dependencies: None.
- Acceptance criteria: `cargo test` passes; an over-limit source is rejected with
  `INVALID_IMAGE`; corrupt/zero-byte inputs produce `invalid`/`Err` with no panic.

### Task 2: Rust — runtime-agnostic batch + partial-failure/large-batch tests

- Goal: Make batch execution testable without a Tauri app and prove one bad file
  never aborts a batch.
- Relevant files:
  - `src-tauri/src/services/batch.rs`
  - `src-tauri/src/commands.rs`
- Implementation guidance:
  - Change `run_batch` signature from `(app: &AppHandle, job_id, files, process)`
    to `(job_id, files, process, on_progress: impl Fn(u32, u32, &str) + Sync)`.
    Replace the `app.emit(...)` calls with `on_progress(done, total,
    &path_string(...))`. Keep the single-file fast path, empty-list
    short-circuit, `min(available_parallelism, 4)` pool, and per-file failure
    capture.
  - In `commands.rs`, update `convert_images`/`compress_images` to pass a closure
    that clones `job_id`/`app` and calls `app.emit(EVENT_PROGRESS, ...)` — the
    same shape `generate_logo_pack` already uses.
  - Add tests to `batch.rs` (using a `noop_progress` closure and a `process`
    closure over real `convert_file`): (a) mixed batch of one valid PNG + one
    corrupt file + one missing path returns `total == 3`, `succeeded == 1`,
    `failed == 2`, and the valid output exists (partial-failure isolation);
    (b) empty list returns `total == 0`; (c) an `#[ignore]`-by-default large
    batch (e.g. 64 small fixtures) completes and reports `succeeded == 64`,
    exercised manually with `cargo test -- --ignored` to check bounded
    completion (not run in normal CI).
  - Document the concurrency rationale (Decision 6) as a short comment on
    `MAX_WORKER_THREADS`/`worker_threads`.
- Dependencies: Task 1 (fixtures assume decode's error behavior), but no shared
  files — can be authored in parallel if the test helper style is agreed first.
- Acceptance criteria: `cargo test` passes including the partial-failure and
  empty-list tests; `cargo build` compiles; the ignored large-batch test is
  available for manual perf verification.

### Task 4: Tool-preference persistence

- Goal: Remember each tool's last settings across sessions (owner-approved).
- Relevant files:
  - `src/services/settings/index.ts`
  - `src/app/providers/SettingsProvider.tsx`
  - `src/tools/batch-workspace/BatchWorkspace.tsx`
  - `src/tools/web-logo-pack/index.tsx`
- Implementation guidance:
  - Extend the persisted settings shape with a nested tool-prefs object:
    `{ tool: { imageConverter: { format?: ImageFormat; quality?: number },
    imageCompressor: { quality?: number }, webLogoPack: { assetIds?: string[] } } }`
    (camelCase, matching existing `PersistedSettings`). Read/write it through the
    same `settings.json` store + `localStorage` boot cache, preserving the
    existing theme/exportPath behavior and the "no-op outside a Tauri runtime"
    catch.
  - In `SettingsProvider`, expose the tool prefs (and a setter) through context,
    with `undefined` meaning "use the component default".
  - In `BatchWorkspace`, seed `format`/`quality` from the stored prefs on first
    mount (falling back to current defaults) and write back on change (debounced
    or on change is fine — the store wrapper already write-throughs). Respect
    `mode` (`convert` reads `imageConverter`, `compress` reads
    `imageCompressor`).
  - In `web-logo-pack/index.tsx`, seed `assets` from stored `assetIds` (preserving
    the full preset list, toggling `on` for saved ids) and write back the selected
    ids on change, after presets are loaded from `getLogoPresets`.
  - Keep resize preferences out of scope (Decision 3).
- Dependencies: None (frontend-only).
- Acceptance criteria: `npm run build` passes; converter format/quality,
  compressor quality, and Logo Pack selection survive an app restart; defaults
  are unchanged when no prefs are stored.

## Risks and open questions

- **Rust/MSVC toolchain is not on this shell's PATH** (it was installed during
  earlier phases but is not exposed here). Tasks 1–3 and 7 require the
  coordinator to run cargo in a toolchain-enabled environment; frontend tasks
  (4–6) do not. Flag any missing-toolchain blocker immediately.
- **Image-size guard thresholds are a judgment call** (`MAX_DIMENSION` 16 384,
  `MAX_PIXELS` 64 MP). These are centralized constants; adjust if a realistic
  workflow legitimately exceeds them. A too-low cap would wrongly reject valid
  images; a too-high cap weakens the OOM protection.
- **`image` 0.25 header-only dimension API** for the pre-decode guard must be
  verified during Task 1 (same crate-API discipline as Phases 2–3). The WebP
  path already guards via `output_buffer_size`; do not double-decode.
- **`run_batch` refactor touches `commands.rs`** (Task 2). It shares
  `commands.rs` with no other task, but the implementer must keep the
  `generate_logo_pack` callback style consistent.
- **Frontend test mocks must cover transitive Tauri imports.** `DropZone`
  imports `getCurrentWebview`, `realAdapter` imports `invoke`/`listen`/plugin
  dialog+opener, and `settings/index.ts` imports `@tauri-apps/plugin-store`.
  Missing mocks will fail tests with obscure errors; Task 5 centralizes them.
- **NSIS build output size / first-build duration** (vendored libwebp + release
  profile) may be slow; the coordinator should budget for a long first
  `cargo build --release`.
- **Tool-preference persistence writes on every change.** The store wrapper
  already write-throughs on each settings change; ensure tool-pref writes reuse
  that path rather than adding a second store instance (avoid double-save
  races). Resize persistence is deliberately out of scope per the owner.
- **Branding is generated**, so it will be a minimal neutral mark, not a
  designer-provided logo. If the owner later supplies art, re-running
  `npm run tauri icon` + a rebuild is a quick follow-up.
